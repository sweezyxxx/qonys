## Repository and traceability requirements

The supplied checklist requires one persistent GitHub or GitLab repository with access for the team, supervisor and committee. Individual accounts and identifiable authorship are required. Work should progress through meaningful commits and reviewed pull/merge requests; meaningful tasks should link to real YouTrack issues with an owner, expected outcome, acceptance criteria and deadline. Each submitted stage must identify its exact version through the required tag convention and provide completed work, limitations and outstanding tasks.

The README must include the title, problem, users, outcomes, team, supervisor, scope, current state, selected technologies and links to YouTrack and documentation. Setup, execution and test instructions become necessary when runnable code exists. The repository structure must cover source code, documentation, editable diagrams and readable exports, tests and configuration examples. Secrets and confidential data must be excluded.

The delivery record separates completed repository checks and actual task creation from pending peer/supervisor review, reader access and the final reviewed stage tag. All three members have identifiable repository contributions; QON-2 was merged through PR 4. Existing authorship is preserved.

## What can be prepared from the available sources

The revised proposal, current scope, draft requirements, diagrams, scenario specifications, comparison updates, evaluation protocol, role-based work breakdown and risk register can be prepared. They must clearly describe intended behaviour and planned evaluation until there is evidence of implementation or measurements.

Actual interviews, client agreements, supervisor feedback, individual contributions, team reviews, repository permissions and tracker assignments require real records. Their absence remains a submission gap even if all written plans are complete.

A complete application is not required for this stage. The required evidence must show that analysis, design, planning and supervision have taken place.

## Prototype requirement for this stage

The stage checklist explicitly requests prototype materials or a prototype link. Its UX row specifies mockups of key user scenarios. Therefore, own screen mockups with clear scenario transitions can address this component without application code. They must be labelled as design/prototype materials and assessed against the actual key user scenarios. A functioning frontend, backend or AI model is not stated as a minimum requirement for this stage.
